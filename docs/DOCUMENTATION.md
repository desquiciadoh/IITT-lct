## 1. Что умеет прототип

| Требование ТЗ | Как сделано |
|---|---|
| Тестовый набор данных | Три участка организаторов встроены. Свой набор загружается как JSON в формате `datasets/*.json`: меню участка → «Загрузить свой набор». Образец формата — там же, «Скачать этот набор» |
| Распределение заявок и порядок визитов | Вставка с сожалением (regret-2) → локальный поиск → ruin & recreate (SISR) со снятием лишних бригад |
| Ограничения: квалификация, время, транспорт | Единый оценщик маршрута `RouteEvaluator`; через него проходит любое решение, включая ручное |
| Карта | Leaflet + OpenStreetMap: маршрут цветом бригады, номер визита, авария — ромб, заявка без исполнителя — пунктирный круг |
| Кто, куда и когда едет | Список бригад с числом заявок и пробегом, расписание бригад по часам, маршрут бригады по порядку |
| События дня | Авария, новая заявка (в том числе точкой на карте), отмена, сход бригады; готовые сценарии, журнал событий, возврат к утреннему плану |
| Что изменилось после события | Новые, перенесённые, сдвинутые, снятые и отменённые заявки; км по бригадам до и после; на карте — затронутые бригады и прежние маршруты пунктиром |
| Объяснения | По заявке: проверенные ограничения и выбор бригады; по бригаде: маршрут; по заявке без исполнителя: причина, разбор по бригадам и что сделать |
| Метрики и сравнение с базовым | Показатели плана с разницей к базовому; экран «Сравнение с базовым»: бригады, суммарный пробег и пробег каждой бригады |
| Дополнительно (ТЗ §2.5) | Ручное переназначение с проверкой; «кто ещё мог бы взять» с приростом км; прогноз опозданий (запас до конца окна меньше 15 мин); базовый вариант на карте; выгрузка плана в CSV |

**Сценарий демонстрации (ТЗ §4):**
1. Открыть участок: на карте заявки по видам работ.
2. «Рассчитать план».
3. Маршруты на карте, расписание бригад внизу, показатели сверху.
4. Щёлкнуть заявку: «Почему эта бригада» и «Другие бригады».
5. «Событие дня» → готовый сценарий (авария, новое подключение, отмена в пути, сход бригады).
6. Панель «Что изменилось» открывается сама.
7. «Сравнение с базовым»: число бригад и пробег по каждой бригаде.

## 2. Схема решения

```
 CSV организаторов ──► python -m app.cli build-datasets ──► datasets/*.json
                                                                 │
 Браузер ◄────────── HTTP /api ──────────► FastAPI (backend/app/api/main.py)
 React + Leaflet                                 │
 (frontend/)                       ┌─────────────┴──────────────┐
                                   │ Solver: вставка, локальный │
                                   │ поиск, ruin & recreate     │
                                   │ Replan: события дня, дифф  │
                                   │ Explain: объяснения        │
                                   └─────────────┬──────────────┘
                                                 │
                         RouteEvaluator (проверка ограничений, стоимость вставки)
                         TravelMatrix (время и км между точками по виду транспорта)
```

- **Интерфейс** — одностраничное приложение на React. Сервер отдаёт собранную версию из `frontend/dist`,
  поэтому интерфейс и API работают на одном порту.
- **Алгоритм** — библиотека без ввода-вывода в `backend/app/solver`. Построение плана, базовый вариант,
  перепланирование, ручное назначение и объяснения проверяют допустимость одним оценщиком маршрута.
- **Данные** — заявки и бригады трёх участков в JSON. Состояние дня (план, события, журнал) хранится в
  памяти сервера.

## 3. Ограничения

| Ограничение | Правило |
|---|---|
| Квалификация | Навык заявки входит в навыки бригады |
| Время | Работа начинается внутри окна заявки. Приехать раньше и подождать можно, начать раньше — нет. Закончить после окна можно, но дорога и работа должны уложиться в смену бригады |
| Транспорт | Если заявка требует тип транспорта, он совпадает с транспортом бригады |

Все три проверяет `RouteEvaluator` (`backend/app/solver/evaluator.py`), другой проверки допустимости в
коде нет. Парные ограничения «заявка — бригада» описаны классами в `constraints.py`: новое ограничение
добавляется новым классом. Тесты проверяют каждый план независимым валидатором
(`backend/tests/helpers.py::assert_plan_valid`).

## 4. Логика оптимизации

**Цель** сравнивается лексикографически, по разъяснениям организаторов:
1. больше выполненных заявок с учётом приоритета: авария 10, подключение 5, ремонт и дозаказ 3;
2. меньше аварий, начатых позже 2 ч от поступления: авария — форс-мажор, ради неё можно вывести ещё
   одну бригаду (ответ экспертов 29.09);
3. меньше задействованных бригад;
4. меньше км, плюс штраф за каждую минуту опоздания аварии и за переезды между Москвой и пригородом.

Ни один шаг поиска не принимает план, который хуже по первым трём уровням, ради выигрыша в км.

**Алгоритм:**
1. Вставка с сожалением (regret-2): сначала аварии, потом подключения, потом остальное. Внутри одного
   приоритета первой ставится заявка, которая потеряет больше всего, если не получит лучший вариант.
   Если на линию нужно вывести ещё одну бригаду, выводится та, что возьмёт больше: длинная смена,
   быстрый транспорт, больше навыков.
2. Локальный поиск: перенос заявки, обмен двух заявок, перенос цепочки из 2–3 заявок, обмен хвостами
   двух маршрутов (2-opt*) и разворот участка маршрута. Дорогие ходы сначала отсекаются точной нижней
   оценкой прироста км. 2-opt* меняет только допустимые хвосты двух уже задействованных бригад и не
   меняет число назначенных заявок или бригад.
3. Снятие лёгких маршрутов: заявки бригады раздаются остальным, если никто не остаётся без исполнителя
   и аварии не опаздывают.
4. Ruin & recreate (SISR, Christiaens и Vanden Berghe, 2020) — основной поиск. Много раз снимаем часть
   заявок и вставляем заново. Что снимаем: соседние по месту и времени заявки, отрезки маршрутов рядом,
   самые «дорогие» заявки, случайные или весь лёгкий маршрут. Вставляем жадно, в случайном порядке и
   с редкими пропусками маршрутов, чтобы поиск не ходил по кругу. План принимается, если не хуже по
   первым трём уровням цели; при равенстве решает отжиг по км.
5. Снятие бригады: заявки самой лёгкой бригады уходят в пул, бригада исключается. Ruin & recreate без
   вывода новых бригад ищет план, где никто не остался без исполнителя, а аварии не опаздывают сильнее.
   Получилось — бригада не выходит на линию.
6. Три независимых запуска шагов 4–5 с разными зёрнами, берётся лучший план. После этого — доназначение
   и локальный поиск по кругу, пока что-то меняется.

Бюджет поиска — число итераций, а не время: одинаковые данные дают одинаковый план на любой машине.
Проверка вставки заявки в маршрут выполняется за O(1): для каждой точки маршрута хранится самое позднее
допустимое начало. Тест сверяет быструю проверку с полным пересчётом на случайных маршрутах.

**Модель времени.** Бригада начинает смену в своей стартовой точке. К следующему клиенту выезжает так,
чтобы приехать к началу окна; ожидание проходит в предыдущей точке. Время в пути зависит от транспорта
бригады (раздел 7).

Расчёт детерминирован: одинаковые данные дают одинаковый план на любой машине.

## 5. Метрики и базовый вариант

Обязательные метрики ТЗ:
- **число задействованных бригад** — бригады, у которых есть хотя бы одна заявка;
- **пробег** по каждой бригаде и суммарно, км.

Дополнительно считаются назначенные заявки, км на заявку, км на автомобилях, время в пути, реакция на
аварии (сколько начато в пределах 2 ч от поступления) и загрузка бригад: (дорога + работа) / смена и
число бригад на линии с загрузкой ниже 50 %.

**Базовый вариант (ТЗ §2.3):** заявки идут в порядке файла. Каждая достаётся первой по списку бригаде,
в конец маршрута которой она допустимо встаёт. Порядок визитов совпадает с порядком назначения.
Ограничения проверяет тот же оценщик.

Метрики видны в интерфейсе (полоса показателей и экран «Сравнение с базовым») и в консоли:
`python -m app.cli benchmark`. Команда с ключом `--update-readme` обновляет таблицу результатов в README,

за 5 мс, самое долгое — 0,2 с на 300 заявках.

## 6. Перепланирование в течение дня

Правила — по разъяснениям организаторов:

- **Начатая работа не прерывается.** Работа заморожена, если бригада уже выехала к клиенту, работает или
  закончила. Бригаду в пути не разворачиваем (наше допущение).
- **Новая обычная заявка** встаёт в свободный интервал бригад на линии. Заявки других бригад не
  переносятся; время может сдвинуться в пределах окон со штрафом за сдвиг. Если места нет, заявка
  остаётся без исполнителя с причиной, а решение вызвать ещё одну бригаду принимает диспетчер.
- **Авария** ставится как можно раньше; ориентир — начать в течение 2 ч от поступления. Она может
  перестроить оставшуюся часть дня. Вытесненные заявки уходят другим бригадам, иначе получают причину
  «вытеснена аварией». Другие аварии новая авария не снимает. Из вариантов постановки выбирается
  тот, где меньше аварий позже 2 ч, затем — меньше снятых заявок, затем — меньше бригад. Снятым
  заявкам поддержка согласует с клиентом новое время (разъяснение 19.09).
- **Отмена** освобождает бригаду, и в освободившееся время ставятся ранее неназначенные заявки. Если
  бригада уже ехала к клиенту, она доезжает и освобождается на месте. Отмена не считается неназначением.
- **Сход бригады:** выполненные и начатые работы остаются за ней, остальные раздаются другим бригадам.
- **Резервная бригада** выводится на линию только при форс-мажоре — аварии или сходе бригады, если без
  этого не обойтись. Её загрузка может оказаться ниже 50 %: по разъяснению экспертов обработка
  форс-мажора важнее. В списке изменений такая бригада помечена.
- **Ручное назначение:** диспетчер выбирает бригаду, заявка встаёт на лучшее место в её маршруте. Если
  назначить нельзя, сервер объясняет почему: нет навыка, занята, смена не покрывает окно. Остальные
  маршруты не перестраиваются.

После любого события каждая заявка находится ровно в одном состоянии: назначена, не назначена с причиной
или отменена. Это проверяет тест с событиями каждые 30–60 мин с 10:00 до 20:00 на всех участках.

| Югоцентр (`southcenter`) | 56 | 56 | 28 | 26 | 0 | 2 | 11 |

- **Авария** — заявка с типом HD «Авария» (разъяснение экспертов 29.09). «Глобальная проблема» с HD
  «Информация» (5 на Востоке, 1 на Югоцентре) — обычный визит в окно клиента: навык «Локальные работы»,
  норматив локальной заявки.
- **Авария на узле.** На Юго-востоке 7 аварий в Кашире и 2 в Ступино — соседние дома с одинаковым окном
  на весь день. Эксперты допускают две модели: отдельный выезд в каждый дом или одна авария на узле,
  из-за которой без связи остались несколько домов. Мы выбрали вторую: в городе области аварии с одинаковым
  окном объединяются в один выезд с нормативом аварии, точка — центр домов. Заявка выезда хранит номера
  остальных строк файла (`covers`), интерфейс их показывает. Вариант «каждый дом отдельно»:
  `python -m app.cli build-datasets --no-node-merge`. Аварии в Москве не объединяются.

**Бригады** построены по контрольному распределению организаторов — реальному дню диспетчеров на тех
же участках. Эксперты (29.09): состав и параметры бригад команда задаёт сама, бригада — виртуальный
сотрудник. Берём бригады, работавшие в контрольный день, и выводим профиль из их истории:

| Параметр | Правило |
|---|---|
| Навыки | Виды работ, которые бригада выполняла: подключение и дозаказ → «Подключение и дозаказы», локальная заявка → «Локальные работы», глобальная проблема → «Аварийные работы». На участке не меньше двух аварийных бригад со сменой 2/2: если меньше, навык получает бригада с самым широким участком |
| Смена | График 2/2 — 10:00–22:00 (в Москве преобладает). График 5/2 — 9 ч: 10:00–19:00, если заявки бригады заканчивались к 18:00; 13:00–22:00, если начинались с 12:00 |
| Старт | Офис участка. Бригада, работавшая только в городе области (Кашира, Домодедово), стартует из дома в своём городе |
| Транспорт | Пригородные и аварийные бригады — автомобиль (расстояния, сварочный аппарат). Остальные по размеру участка: один район — пешком или на велосипеде, два — общественный транспорт, три и больше — автомобиль |

| Участок | Бригад | 2/2 | 5/2 | Авто | Общ. транспорт | Пешком | Велосипед | С аварийным навыком |
|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| Восток | 12 | 9 | 3 | 6 | 3 | 2 | 1 | 4 |
| Юго-восток | 12 | 7 | 5 | 6 | 2 | 2 | 2 | 4 |
| Югоцентр | 11 | 7 | 4 | 4 | 4 | 2 | 1 | 3 |

**Требуемый транспорт** в CSV не задан, поэтому задаётся правилом: авария (сварочный аппарат для оптики)
и «Работа с кабелем» (бухта кабеля и лестница) — только автомобиль. Таких заявок 5, 8 и 2 по участкам.

**Единицы.** Время — `ЧЧ:ММ` и минуты от полуночи (`start_min`, `end_min`), длительность — минуты,
расстояние — км, координаты — широта и долгота в градусах (WGS 84).

**Заявка** (`*.orders.json`):

| Поле | Смысл |
|---|---|
| `id` | номер заявки |
| `work_type` | вид работ: `emergency` авария, `connection` подключение, `local` ремонт, `addon` дозаказ |
| `skills` | требуемый навык (из вида работ) |
| `priority` | `urgent` у аварий, `normal` у остальных |
| `window` | окно начала работ: 2 ч с чётного часа; у аварий Юго-востока, кроме одной, — весь день |
| `duration_min` | чистое время работ, мин |
| `required_transport` | требуемый транспорт или `null` |
| `location` | адрес, район, координаты |
| `bk_type`, `hd_type` | типы заявки в классификаторах BK и HD из исходного файла |
| `tech` | технология подключения (FMC/FTTB) и гигабит, если есть в исходном файле |
| `released_min` | когда заявка поступила (для событий дня), мин от полуночи |
| `covers` | авария на узле: номера других строк файла, которые закрывает этот выезд |

**Бригада** (`*.engineers.json`): `id`, `name`, `skills` (1–3 навыка), `transport`, `shift` (смена),
`depot` (стартовая точка). Бригада — один исполнитель.

**Справочники:**

| Навык | Виды работ |
|---|---|
| `connection` — подключение и дозаказы | подключение, дозаказ |
| `local` — локальные работы | ремонт, глобальная проблема без аварии (HD «Информация») |
| `emergency` — аварийные работы | авария |

| Вид работ | Норматив, мин | Чистая работа, мин |
|---|:-:|:-:|
| Подключение | 90 | 70 |
| Авария | 100 | 80 |
| Ремонт | 50 | 30 |
| Дозаказ | 40 | 20 |

Нормативы — из файла организаторов «Нормативы.xlsx». В каждый входят 20 мин брони на дорогу; их заменяет
рассчитанное время в пути, поэтому в план идёт чистое время работы.

| Транспорт | Скорость |
|---|---|
| `car` — автомобиль | 30 км/ч |
| `transit` — общественный транспорт | 18 км/ч + 5 мин на посадку |
| `bike` — велосипед | 12 км/ч |
| `foot` — пешком | 4,5 км/ч |

Расстояние — по прямой × 1,35 (поправка на городскую сеть улиц).

## 8. Допущения

Разъяснения экспертов 29.09 закрыли большую часть вопросов; ниже — что из них следует для модели и
что мы решили сами.

- Горизонт — один день, время московское. Возврат в стартовую точку не нужен, обед не планируется.
- Окно заявки — интервал начала работ. Каждая строка исходного файла — отдельный выезд, кроме аварий
  на узле в городах области (раздел 7).
- Авария — по полю HD «Авария». Аварии известны с утра: для аварии с окном на весь день реакция
  отсчитывается от начала рабочего дня (10:00). Для аварии, поступившей днём (событие дня), — от момента
  поступления. Ориентир реакции — 2 ч.
- Бригады и их параметры задаём сами по контрольному дню (раздел 7). Смены — графики 2/2 и 5/2.
- Резервную бригаду днём выводим только при форс-мажоре (авария, сход бригады); её загрузка может быть
  ниже 50 %.
- Пробег — все км, любым транспортом. Км на автомобилях показываются отдельно (подсказка у пробега).
- Загрузка бригады — (дорога + работа) / длина смены. Бригада на линии с загрузкой ниже 50 % —
  «лишний человек» (ориентир организаторов); при сравнении планов считаем такие бригады.
- Координаты адреса — центр района плюс детерминированный сдвиг до ±1,2 км. Для бригад Каширы и
  Домодедово стартовая точка — их город, для остальных — офис участка.
- Требуемый транспорт задан правилом (раздел 7).
- Бригада в пути к клиенту не разворачивается; сошедшая бригада заканчивает начатую работу.

## 9. Известные ограничения и развитие

**Ограничения прототипа:**
- Координаты приблизительные, расстояния — по прямой с поправкой, маршруты на карте — прямыми линиями.
  Скорость на трассе та же, что в городе, поэтому переезд Москва ↔ Кашира занимает около 4 ч.
- На Юго-востоке одна авария из пяти начинается позже 2 ч. Утром в Кашире и Ступино пять срочных дел
  на две местные бригады: две аварии на узле, два подключения и ремонт в окне 10–12. Бригаде из
  Москвы туда около 4 ч. Начать обе аварии вовремя можно, только сняв одну из утренних заявок, а
  назначенные заявки в цели важнее. Эталон OR-Tools приходит к тому же.
- Профили бригад выведены из одного контрольного дня.
- Загруженные наборы и события дня хранятся в памяти сервера и пропадают при перезапуске.
- Исходные CSV организаторов через интерфейс не загружаются, только JSON в нормализованном формате.
- Оборудование бригад не учитывается.

**Развитие:**
- Геокодирование адресов и расстояния по дорогам (OSRM), маршруты на карте по улицам.
- Учёт оборудования: запас на бригаду и проверка при перепланировании.
- Гибкие окна: с окнами 4 ч вместо 2 ч тот же алгоритм обходится меньшим числом бригад и км
  (`python -m app.cli benchmark --wide-windows`), это можно предлагать клиентам как опцию.
- Перенос вытесненной заявки на более позднее окно с пометкой «сообщить клиенту» вместо «не назначена».

## 10. API

Интерактивное описание — http://localhost:8000/docs.

| Метод и путь | Назначение |
|---|---|
| `GET /api/health` | сервер работает |
| `GET /api/datasets` | список участков |
| `GET /api/dataset/{регион}` | заявки и бригады без расчёта |
| `POST /api/datasets/upload` | загрузить свой набор (JSON) |
| `POST /api/plan/solve` | рассчитать план |
| `GET /api/plan/{регион}` | текущий план |
| `POST /api/plan/event` | событие дня или ручное назначение (`manual_assign`) |
| `POST /api/plan/reset/{регион}` | вернуть утренний план |
| `GET /api/scenarios/{регион}` | готовые сценарии событий |
| `GET /api/alternatives/{регион}/{заявка}` | какие бригады ещё могли бы взять заявку |
| `GET /api/explain/{заявка}` | объяснение по заявке |

    replan/          разрез дня на момент события, правила событий, дифф, альтернативы

    explain.py       объяснения по итоговому плану

  cli.py         build-datasets | solve | benchmark
  bench/         стенд качества: генератор сценариев, независимая проверка, эталон OR-Tools

backend/tests/   тесты: оценщик, поиск, солвер, перепланирование, API, данные, сценарии стенда
frontend/src/    React 19 + Vite + Tailwind 4 + Leaflet
  state/         состояние рабочего места диспетчера
  components/    шапка, показатели, списки, карта, расписание, панель справа, события, сравнение

datasets/        нормализованные данные трёх участков
